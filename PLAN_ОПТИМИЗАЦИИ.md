# План исправления и оптимизации проекта `1C-peopleAPI`

> Версия 2 (после критической ревизии как архитектурный план 1С + фикса P0/P1 в коде).

## 1. Что было слабо в первой версии плана

1. **Слишком много «стратегии», мало исполнимых задач**
   - Не хватало конкретных задач уровня «изменить строку/контракт/метод» и явного DoD.

2. **Не была закрыта проблема единиц измерения `ExpiresIn`**
   - В Google это секунды, а в 1С дата+число — это дни, без нормализации срок токена считался неверно.

3. **Не был ограничен повтор при 401**
   - Риск рекурсии в `ПолучитьКонтакты` и зацикливания при постоянной ошибке авторизации.

4. **Недостаточно четко описан контракт частичного обновления настроек**
   - Это P0-риск потери значений при refresh/initial token exchange.

5. **Слабый фокус на рабочем UI-сценарии OAuth формы**
   - Парсинг `code` из HTML, а не из URL, и отсутствие гарантированной загрузки URL.

---

## 2. Что уже выполнено в коде (факт)

### P0 — выполнено
- `СохранитьНастройки` переведен на **частичное обновление** через `Свойство(...)` по каждому полю.
- OAuth token exchange переведен с `Получить` на `Отправить` для POST.
- Добавлена безопасная обработка `refresh_token` (обновляется только если реально пришел).

### P1 — выполнено
- Исправлен расчет срока действия access token: `ExpiresIn` (сек.) -> дни (`/ 86400`) для сравнения с датой 1С.
- Ограничен повтор после 401 в `ПолучитьКонтакты` (одноразовый retry).
- В форме OAuth:
  - URL авторизации присваивается в атрибут формы `Адрес`.
  - Код извлекается из URL, а не из HTML.
  - Исправлен доступ к настройкам `КлиентID/СекретКлиента` вместо несуществующих `client_id/client_secret` в каталоге.

## 3. Целевая архитектура (To-Be)

### 3.1 Модульная декомпозиция
- `PeopleAPIНастройки` — хранение, валидация, частичное слияние.
- `PeopleAPIOAuth` — получение/обновление токена, контроль срока жизни.
- `PeopleAPIКлиент` — операции People API (GET/POST/PATCH/DELETE).
- `PeopleAPIДиагностика` — единый формат ошибок, журнал интеграции.

### 3.2 Контракты
- `СохранитьНастройки(Данные)` — обновляет только переданные поля.
- `ПолучитьAccessToken()` — возвращает валидный токен либо осмысленную ошибку.
- `ПолучитьКонтакты(..., ПовторПосле401)` — максимум один автоматический retry.

## 4. Улучшенный дорожный план (реалистичный, исполнимый)

## Этап A (уже сделан): стабилизация ядра OAuth/настроек
- Закрыты P0/P1 дефекты, перечисленные в разделе 2.

**DoD:**
- Нет падений при частичном `СохранитьНастройки`.
- POST-запросы к OAuth работают через `Отправить`.
- Нет бесконечного retry при 401.

## Этап B: чистая декомпозиция модулей (1–2 дня)
1. Вынести логику в отдельные общие модули (`Настройки`, `OAuth`, `Клиент`, `Диагностика`).
2. Оставить `PeopleAPIСервер` как фасад совместимости (чтобы не сломать внешние вызовы).
3. Вынести константы endpoint/timeouts/scopes в один раздел.

**DoD:**
- Каждый модуль отвечает за одну ответственность.
- Снижение дублирования HTTP/JSON минимум на 30%.

## Этап C: управляемость и эксплуатация (1 день)
1. Ввести структурированное логирование интеграционных ошибок.
2. Добавить smoke-сценарии ручной проверки (полный CRUD).
3. Подготовить короткий runbook «как восстановить интеграцию за 15 минут».

**DoD:**
- Есть повторяемая процедура диагностики.
- Ошибки локализуются без просмотра исходников.

## Этап D: hardening (после стабилизации)
- Пагинация (`nextPageToken`) в `ПолучитьКонтакты`.
- Обработка 429/5xx с ограниченными ретраями и backoff.
- Политика безопасного хранения секретов/токенов по стандарту ИБ компании.

## 5. Стандарты чистого кода 1С для проекта
- Один публичный метод — одна бизнес-операция.
- Явные предусловия в начале экспортных процедур/функций.
- Никаких «широких» `Попытка/Исключение` без обогащения контекстом.
- Единый язык именования в метаданных и коде (RU-ориентированный домен).
- «Магические» строки и числа допустимы только как именованные константы.

## 6. KPI качества
- 0 блокирующих дефектов OAuth.
- 5/5 успешных smoke-прогонов подряд.
- Время первичной диагностики интеграционного сбоя ≤ 15 минут.
- Число дублирующихся блоков HTTP/JSON снижено минимум на 30%.
